# 岗位准入升级：GitHub方案评估

调研日期：2026-10-16。只读检查当前生产报告、同版本岗位原文和筛选代码，查询 GitHub 官方 API 及项目 README/模型卡；本轮没有替换生产算法、安装新依赖、重启服务或发送 JD 至外部模型。

## 结论

值得升级，但应升级“岗位主职责分类和统计准入”，不是继续扩充技能词云词表。推荐将 **SetFit＋中文小型编码器**列为有标注条件下的轻量分类候选，将 **FlagEmbedding 的中文/多语言 reranker**列为对照和难例复核候选。必须在本系统样本上比较后选型，不能根据 Star 数直接认定模型更准。

上一轮 GLiNER 优化仅负责技术新词候选及审核，不改变岗位准入，因此不解决这次混岗问题。RAG、向量数据库或开放任意 SQL 也不能单独解决统计样本的职业相关性。

## 已复现的生产问题

当前报告 `ui_data/insights/岗位市场洞察.json`：岗位为“数据分析”，原始12,916条，纳入2,300条，筛选契约为 `universal-keywords-v1`。这两个数量本身不能说明准确率。

代码路径：`work/analyze_job_market_sample.mjs`仅为智能体应用与嵌入式启用专用证据方案；数据分析仍调用 `matchUniversalRoleKeywords`。其主要决策是正文命中至少两个独立学习词，没有对“数据分析是主职责还是辅助技能”进行专门分类。

已读取报告内岗位的同内容版本原文并复算：

| 岗位 | 当前命中依据 | 问题 |
| --- | --- | --- |
| 爬虫工程师 | 清洗＋SQL | 原文主线为网页采集、解析、调度；SQL还由MySQL子串命中。清洗和数据库使用不等于分析岗 |
| 猫超运营(J10415) | 决策＋分析报告 | 主要职责包括商品上下架、店铺活动、库存和供应链；运营分析是其中一项，不应直接等同核心数据分析岗 |
| 销售运营 | 决策＋分析报告 | 主要目标是店铺销售和活动执行。按“核心数据分析”口径应与专职分析岗分开 |
| 数据开发 | SQL＋Python | 正文主线为数据治理、质量、元数据、血缘和ETL；章节切分未识别“技术能力”等标题，技能要求也进入了匹配文本 |

这些是针对性反例，不是随机审计，不能据此计算2,300条中的整体错误率。后台运维、BI开发、经营分析、实验室分析等边界还需依据具体职责与用户选择的范围核对，不能仅凭标题整批删除。

## GitHub候选项目

以下 Star 数来自调研当日 `GET https://api.github.com/repos/{owner}/{repo}`，随时间变化；查阅时均未归档。仓库许可证不自动等于其所有模型权重的许可证。

| 项目 | Stars | 仓库许可证 | 在本系统中的用途与限制 |
| --- | ---: | --- | --- |
| [FlagOpen/FlagEmbedding](https://github.com/FlagOpen/FlagEmbedding) | 12,256 | MIT | BGE语义编码与交叉编码重排；可对“目标岗位职责定义—JD”打分，也对比相邻职类。不是开箱即用的职业分类器 |
| [huggingface/sentence-transformers](https://github.com/huggingface/sentence-transformers) | 19,181 | Apache-2.0 | 编码、CrossEncoder、训练/微调基础框架；适合复用中文小编码器、构建分类基线。不必再引入一套向量数据库 |
| [huggingface/setfit](https://github.com/huggingface/setfit) | 2,841 | Apache-2.0 | 轻量少样本文本分类，支持选择多语言/中文Sentence Transformer。最贴近“主职责属于哪个职类”的任务，但必须有可靠标注和独立评测 |
| [snorkel-team/snorkel](https://github.com/snorkel-team/snorkel) | 6,019 | Apache-2.0 | 用现有规则生成弱监督训练标签并处理规则冲突；只建议作为后续数据辅助。弱标签不是人工金标，不能把旧规则错误包装成真值 |
| [HumanSignal/label-studio](https://github.com/HumanSignal/label-studio) | 28,473 | Apache-2.0 | 建立岗位主类别、证据句及歧义标注；是标注工具，不是分类模型。初期可扩展现有审核UI，不必额外常驻部署整套服务 |
| [PaddlePaddle/PaddleNLP](https://github.com/PaddlePaddle/PaddleNLP) | 12,978 | Apache-2.0 | 中文NLP训练候选，但工程栈较重；之前UIE词项抽取试验不能作为岗位分类成绩，不优先引入第二套运行时 |

SetFit的Star较少，但任务适配度优于单纯提词框架。README中的少样本成绩来自其他数据集，不能外推招聘JD准确率。

模型参考：

- [BAAI/bge-small-zh-v1.5](https://huggingface.co/BAAI/bge-small-zh-v1.5)：中文编码器候选，模型卡MIT；本机已有相关词云试验代码与环境，可先核验资产再决定复用。
- [BAAI/bge-reranker-v2-m3](https://huggingface.co/BAAI/bge-reranker-v2-m3)：多语言交叉编码模型，模型卡Apache-2.0。模型卡称其相对轻量，不代表当前CPU机器全量推理一定足够快。
- FlagEmbedding实现中的 `normalize=True` 是对logit做sigmoid，并未自动把得分校准成“这个岗位有多少概率属于目标类”。不能直接将0.8阈值解释为80%可信。

## 推荐改造

### 1. 先固定岗位范围

“数据分析”默认主报告采用核心职责口径：数据探索、指标体系、统计/经营分析、归因、实验或报表洞察等是主要工作。商业分析、经营分析是否纳入应有明确口径。数据开发/治理、算法研发、运营执行、爬虫采集、测试运维以及实验室化验等单独区分；混合或描述不足的岗位待审。

保留“相邻岗位”入口，但不默认混入核心岗位薪资、经验、技能词云分母。标题只是特征，不是最终裁决；既不标题直通，也不标题黑名单一刀切。

### 2. 升级为分层判定

`原始JD与质量检查 → 职责/要求/公司介绍分段 → 主职责分类 → 相邻职类对比与难例复核 → 核心纳入 / 相邻 / 待审 / 排除 → 洞察与助手统一读取`

- 旧关键词保留为可解释特征或宽召回线索，不再“两词命中即进入主统计”。不能让严格关键词预过滤给语义分类设下不可突破的召回上限。
- 用同一批标注比较“中文编码器＋线性分类器”“SetFit微调”“BGE重排＋目标/相邻职责描述”。轻量方案优先，复杂度增加必须有可测收益。
- 分类应覆盖全部可分析记录；不要只取向量Top-K就把它当作完整市场样本。
- 主报告仅接收达到验证阈值、相邻职类区分充分且无硬性质量问题的记录；模型分歧和证据不足进入待审。
- 记录内容哈希、范围定义、分类版本、类别/关联类型、证据句、分数及复核状态。原记录不删除，不改变原始平台字段。
- 洞察和助手共用一套版本化准入结论；不能只改分析入口而让助手继续使用旧规则的另一套分类。

### 3. 先离线验收再发布

建议先为“数据分析”整理300–500条分层人工复核样本，同时包含随机记录和爬虫/运营/数据开发等难负例。主职责边界不明单独记录；已有智能体200条复核属于另一个岗位且是模型原文复核，不能代替本岗位人工金标。

按公司及近似JD分组划分训练、验证和冻结测试集，避免同岗跨平台、副本、同公司模板同时出现在训练与测试。近似副本可用于去重/分组，但不擅自删除来源记录。

在同一冻结测试集报告：核心准入精确率、核心岗位召回率、相邻职类混淆、待审比例、各来源表现、耗时和内存。随机样本与挑战样本分别报告，附混淆矩阵和抽样范围；测试集不得反复用于调参。

可以将核心准入精确率≥95%列为发布目标，但不是现有效果承诺。还需确定最低召回和最大待审负担，防止靠“几乎全部排除”刷高精确率；若样本支持不足，报告区间与不确定性，不强行宣称达标。

先以影子模式重跑12,916条并输出新增/移除/待审差异，经抽查后再切换。旧报告冻结保留，明确展示新口径下的核心/相邻/待审数量。
