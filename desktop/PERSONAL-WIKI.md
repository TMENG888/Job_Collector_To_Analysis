# 个人 Wiki 与版本简历库

入口：桌面 App 顶部「个人资料」，或 Web `/profile`。自动优选简历和 Wiki 定制已接入**桌面 App 原生岗位插件**；旧 Web 扩展插件暂不自动选版，不能据此认为两个插件都已支持。

## 使用顺序

1. 在「材料与核实」导入 PDF、PNG/JPEG、DOCX/TXT/MD，或公开 GitHub 主页/仓库。单文件最多 3MB；PDF 必须可解析，最多 6 页。DOCX 作为材料解析，成为可投递简历前仍需自行转 PDF。
2. 勾选模型共享与预算后，启动 Wiki 整理智能体；也可勾选本次上传后自动整理。图片先使用本机 Windows OCR，不上传原图；可以另存人工转录。GitHub 仓库通过公开 API 固定到 commit，读取 README、有界文件树及最多7份额外的文档、依赖清单、代表性源码（正文总量约4万字）。不执行代码；过滤私密配置与构建产物。个人主页仍只作最近10个仓库的目录，需另导入具体仓库分析实现。历史 README 快照可直接语义整理；要补充源码须重新导入仓库地址。
3. 智能体先规划阅读，再按片段提炼语义能力条目，最后由独立一次模型请求审查证据支持、重复与冲突。每轮最多3份材料，每份最多8个阅读片段，非全仓审计；界面报告实际阅读覆盖范围、Token及估算费用。阅读快照先按原始行脱敏，再切为最多900字的证据单元及6000字的阅读片段；超长行继续分段，不丢弃6000字以后的部分。读取仍受现有40片段及GitHub导入快照上限约束，不代表完整读取仓库。

   模型仅返回已读证据单元编号（如 `c0:e1`），程序填入对应脱敏原文、固定版本路径/行号/列号及哈希，模型不再抄写引用。不接受原文模糊匹配、模型自造引用或其他阅读批次的编号。编号存在不等于陈述正确，独立审查仍须确认语义支持、求职价值、重复与冲突，项目功能不自动归因到本人。单条编号/归属/结构错误或缺少完整审查时隔离该条，其他条目只有经过独立审查才可发布。若所有候选无效、请求/预算失败或取消，不覆盖旧候选。每轮仍在处理结束时原子发布可用结果，不发布未审查的中间内容，也不自动付费重试。

   「查看阅读范围、用量与诊断」报告失败阶段、提炼批次、条目序号和固定错误码，不保存或展示任意模型输出作为诊断。问题记录随加密状态持久保存（最多80项）；后台运行可查看进度、停止，重启中断不会自动续费。证据协议升级后旧范围材料需手动整理，历史确认和已批准PDF的原有证据哈希不自动改变。
4. 整理范围仅服务简历制作和 JD 匹配：保留有证据的技术技能、项目简介/关键实现/职责/成果、获奖与证书，以及必要的教育、实习与工作经历、求职资格。不整理生活随笔、操作手册、界面细节、版本历史、安装配置、备份说明或纯依赖列表。规划、提炼、独立审查三步都使用这一范围；审查会拒绝“真实但与求职无关”的候选，再按简历价值优先级每份最多保留12条，允许零条。相关实现应合并，不复述更新日志。该上限针对每轮每份材料的新候选，历史人工确认内容不自动裁剪。
5. 人工核对候选与原文，仅勾选真实且属于自己的经历/贡献。未经确认的候选不用于匹配。新导入不再生成逐行分类碎片；历史未核实碎片从候选/API展示中隐藏，也不能直接确认，原始加密材料仍完整保留。历史已确认事实继续保留，可在材料详情取消勾选以撤销。旧整理范围的材料会标为待整理，需用户授权后重新运行，不自动联网或产生费用。AI 的语义审查并非真实准确率证明，也不替代人工贡献核实。
6. 在「简历库」逐页预览并批准原始 PDF。也可粘贴完整 JD，由 AI 判断已核实 Wiki 证据是否足够，再选择、排序已经人工确认的语义条目，生成新的 PDF 草稿；未确认的提炼结果不可进入简历。人工应检查版式与上下文完整性。
7. 回桌面「求职浏览器」插件，从简历库**选用**活动版本，生成搜索方案。勾选「优选库存」和「Wiki 生成草稿」后，系统先用已有监督分类器筛岗位，再对最多 3 个词法排序靠前的已批准简历依次评估。达到证据阈值即采用；这不是对整个库的穷尽排名。
8. 没有适配库存，但 Wiki 证据足够时，生成草稿并停止本批；到个人资料审核后，回插件选用并**重新授权**。批准不等于同意发送，旧批次不会自动恢复。Wiki 证据不足、硬性资格未知或结果不可溯源时不编造、不发送。

## 误传材料删除与恢复

材料清单每行及详情均有「删除」入口，点击后须确认具体文件名。删除采用可恢复的逻辑删除：从材料清单、Wiki 与岗位匹配中停用该来源；相关人工转录一起移入回收站，上传 PDF 从活动简历库隐藏，依赖其证据的定制简历失效并清除批准。删除不会修改电脑上的原始文件，也不会物理擦除加密快照。

在材料清单底部展开「回收站」可确认恢复；原文及原有事实核实结果保留，但简历批准和旧预览票据不恢复，必须重新逐页预览批准，再授权求职批次。重复导入后若同一材料已有活动副本，不允许重复恢复。整理运行中暂不允许删除/恢复，请先停止并等待完成。接口要求本机同源 JSON 和显式确认，不提供无确认永久删除。

## 审核与发送的绑定

- 审核票据有效 10 分钟，绑定不可变 PDF SHA256 和全部页面截图 SHA256；每次批准生成独立审批 ID。
- 事实核实与 PDF 批准是两项独立操作。新 PDF 不继承旧 PDF 批准。
- 发送批次仅允许启动时快照中的已批准版本；批次中新增/新批版本不会自动加入授权。
- 选择了另一份库存 PDF 时，匹配使用该份的正文，招呼引用该份证据，发送该份的页面，不混用活动简历图片。
- 开启会话、发招呼、发送每页图片前再次核验批准、证据及文档哈希。撤销批准、归档来源、撤销引用事实都会使关联定制版本不可发送。
- 保留原有岗位指纹校验、收件人核验、防重账本和频率保护。发送结果不明即停止，不自动重试。账本记录实际简历 ID 和 PDF 哈希，不写简历正文。

## 存储、隐私与限制

个人资料默认位于 `E:/Codex/work/20261020-personal-wiki/runtime/<数据目录哈希>`，可用实际支持的 `JOB_PERSONAL_WIKI_DIR` 指定。Web 服务与 App 必须使用同一数据目录/同一覆盖路径和 Windows 账户。

原始文件、事实、版本和日志采用 AES-256-GCM 加密并压缩；密钥由当前 Windows 用户 DPAPI 包装。Wiki 页面为这些证据的动态视图，不另写未加密 Markdown 原文。需要备份时同时保留目录和当前账户解密条件；没有实现跨账户迁移/密钥恢复。

活动简历闲置 30 分钟只清内存，不删除持久简历库。归档与撤销为逻辑失效，原始资料仍加密保留。OCR 临时文件在同一 E 盘目录下处理并清理。不要把运行目录、私人材料或凭据提交 GitHub。

模型仅在人工勾选共享并触发操作后处理脱敏文本，截图含原始个人信息，只在逐页核对并授权后用于 HR 发送。脱敏不是匿名保证，上传和发送前仍应检查材料。预算沿用现有 DeepSeek 估算价格，不是实际账单。
